# The public API, reshaped once for 1.0

Status: agreed design, 2026-09-27. Issue #15 (its Medium and Low items that break the API). Ships as
0.3.0; after it the API is frozen and 1.0 follows.

## Intent

Every breaking change the API still needs is made at once, while there is a single consumer, so that
1.0 can promise stability for years. The measure of success: one calling style, one shape for a
problem, names that collide with nothing, and result objects that hold still.

Out of scope, because they can be added after 1.0 without breaking anything: sheet addressing by
name, sheet visibility, a partial `CsvDialect` override, cheap single-sheet analysis, async import,
`IDataReader`. They stay on #15.

No `[Obsolete]` bridges: old names are removed, not kept beside the new ones. The single consumer
adapts once, and the changelog carries an old → new table.

## 1. One calling style: static, options as a parameter

As `JsonSerializer` does. The layers hold no state that would justify instances.

```csharp
FileProfile profile = TabularAnalyzer.Analyze(cursor, options: null, progress: null, cancellationToken);
ExtractionSession session = TabularExtractor.Start(cursor, plan, schema, options, cancellationToken);   // unchanged
ImportRun<T> run = TabularImporter.Import(stream, name, plan, schema, map, options, cancellationToken);  // unchanged
```

`TabularAnalyzer` becomes a static class: `Analyze(ITabularCursor cursor, AnalysisOptions? options =
null, IProgress<AnalysisProgress>? progress = null, CancellationToken cancellationToken = default)`.
The constructor and the two instance overloads go.

## 2. One shape for a problem

`RowError`, `MappingFault` and `PrecheckFinding` stay three types — a row that failed, a plan that
does not fit its schema, and a prediction from the profile are different things, and the compiler
keeps them apart — but they share their names and an interface:

```csharp
public interface ITabularProblem
{
    string Code { get; }          // the meaning; a UI translates it
    string? FieldName { get; }
    int? ColumnIndex { get; }
}
```

- `TargetFieldName` → `FieldName`, `SourceColumnIndex` → `ColumnIndex` on all three, on
  `ColumnBinding` and on `TabularStructureException` (`ColumnIndex`). `RowError` keeps them non-null
  and implements the interface explicitly where the types differ.
- **`PrecheckFinding.Detail` is removed.** Its English sentences carried data; the data becomes fields:
  - `AffectedRows` (`int?`) with `AffectedRowsBound` (`Exact`, `AtLeast`, `AtMost`) — the profile can
    say "at least 12 rows" or "up to 40 rows", which a bare number misstated;
  - `Examples` (`IReadOnlyList<string>`) — up to five values that fail the rule, as the profile kept them;
  - `Arguments` (`IReadOnlyDictionary<string, string>`) — the values a message for this code needs
    (`sheetIndex`, `culture`, `expectedHeader`, `actualHeader`, `headerRow`, `distinctCount`,
    `columnCount`, …), named per code and listed on the error-code page, so a UI fills its own
    translated template.
- `MappingFault` gains nothing but the renames; `RowError` keeps `RowNumber` and `RawValue`.

## 3. Names that collide with nothing

- **Fields.** `TargetField` → `ImportField`, the abstract base, which also carries the factory
  methods that today live on the static class `ImportField`:
  `ImportField.Text("name")` returns a `TextImportField`. Likewise `IntegerImportField`,
  `DecimalImportField`, `DateImportField`, `BooleanImportField`. `TranslatedField` →
  `TranslatedImportField`. The fluent methods are unchanged.
- **Schema.** `TargetSchema` → `ImportSchema`.
- **Constraints** gain the suffix `Constraint`: `ExactLengthConstraint`, `MinLengthConstraint`,
  `MaxLengthConstraint`, `MinValueConstraint`, `MaxValueConstraint`, `AllowedValuesConstraint`,
  `PatternConstraint`, `RuleConstraint`. `FieldConstraint` stays. The motivation is concrete:
  `[MaxLength(100)]` in an entity is ambiguous once a file uses both `System.ComponentModel.DataAnnotations`
  and `TriasDev.Tabular`.
- **Binding.** `ColumnBinding.SourceHeader` → `Header`, beside the renames in section 2.

## 4. A run reads once, and says so

`ImportRun<T>` is no longer an `IEnumerable<ImportOutcome<T>>`. It reads the file once, through one of:

```csharp
IEnumerable<ImportOutcome<T>> ReadRows(CancellationToken cancellationToken = default);
IEnumerable<ImportChunk<T>> ReadChunks(int size, CancellationToken cancellationToken = default);
ImportResult<T> ReadAll(int limit = 100_000, CancellationToken cancellationToken = default);
```

A second read, by any of them, throws `InvalidOperationException` ("an import run reads its file
once"). `Rows`, `InChunks`, `All` and `GetEnumerator` go. Every read takes the token, which
`foreach (var o in run)` could not pass.

## 5. Results that hold still

- `ExtractionSummary` becomes an immutable record; `ImportRun<T>.Summary` and
  `ExtractionSession.Summary` return a snapshot taken when read. The counters the run keeps are
  internal.
- **Data records compare by value, collections included**: `MappingPlan`, `ColumnBinding`,
  `AnalysisOptions` (its `Cultures`), and any other record whose members are collections of values.
  Two plans with the same bindings are equal, and a plan survives a round trip through storage as an
  equal one. Implemented with `Equals`/`GetHashCode` overrides that compare sequences element by
  element.
- **Schema objects compare by reference, and say so by being classes**: `ImportField` and its
  subtypes, `FieldConstraint` and its subtypes. They carry delegates and compiled patterns, for which
  value equality is not meaningful. The fluent methods copy internally as `with` does today.

## 6. Moving to a sheet can be cancelled

`ITabularCursor.MoveToSheet(int index, CancellationToken cancellationToken = default)`. Every cursor
checks the token as it reads towards the sheet: the ods cursor in its forward scan, the archive
cursor while it copies a workbook, the xlsx cursor while it opens a sheet part. The analyzer, the
extractor and the importer pass their own token. The KNOWN-ISSUES entry goes.

## Documentation and release

- The guide pages, the samples, `README.md`, the `llms.txt` description in `mkdocs.yml` and the XML
  docs follow the new names; the error-code page lists each precheck code's `Arguments`.
- The commits are `feat!:` / `refactor!:` with a `BREAKING CHANGE:` footer, so release-please (with
  `bump-minor-pre-major`) proposes 0.3.0. The changelog gets an old → new table.
- `PublicAPI.Shipped.txt` loses the removed lines and `Unshipped` gains the new ones; package
  validation against 0.2.0 is expected to report the breaks, so the baseline check is suppressed for
  exactly these changes (a `CompatibilitySuppressions.xml` generated once), not disabled.

## Verification

- The existing suite, renamed, passes: behaviour does not change, only its names and shapes.
- New tests pin what is new in behaviour:
  - a second read of an `ImportRun` throws, by each read method;
  - a `Summary` taken before a read does not change during it;
  - equal plans are equal and hash alike, and a plan differing in one binding is not;
  - `MoveToSheet` with a cancelled token throws `OperationCanceledException`, for each cursor, and for
    the archive and ods cursors while mid-way to a sheet;
  - every precheck code fills the `Arguments` its entry on the error-code page names — checked by a
    catalog test, as the error codes are.
- The read path does not change: the benchmark is run once on the 5M csv and the million-row
  workbook to confirm it.
